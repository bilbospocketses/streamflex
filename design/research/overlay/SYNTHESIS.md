## 1. Bottom line

The approach is viable, and the four research passes agree on that; what they changed is *where the ceiling is and how the extension gets into the browser*. On Windows the three targets are Edge, Chrome and Firefox (decision), and Edge is the quality leader and the recommended default: it is the only browser that gives Netflix 4K **and** HDR/Dolby Vision **and** 5.1/Atmos (VERIFIED, Netflix Help), and Chrome now matches it on Netflix resolution alone (4K via PlayReady SL3000, Chrome 140+ x64, VERIFIED) but not on HDR or audio (REPORTED). Every other DRM service caps a desktop browser at 1080p or less regardless of browser (Disney+, Prime, Apple TV+ VERIFIED; Max has no browser on its 4K list, VERIFIED; Hulu 720p REPORTED), so "4K in a browser" is a Netflix-and-YouTube story, and the honest Windows ceiling for the catalog as a whole is 1080p stereo with Netflix and YouTube as the 4K exceptions. On Linux the targets are Chrome, Edge and a full (non-snap) Firefox (decision). Chrome and Firefox share one ceiling, Widevine L3 (R1 §Q5; R5 §1.4). R1 puts Edge at the same L3, but R6 finds that **whether Edge on Linux plays Widevine content at all is UNKNOWN, leaning "no" on current stable** (§3, §6). Where it plays, the L3 ceiling is: Netflix nominally 1080p but 720p by default in practice (VERIFIED table vs REPORTED practice), Prime SD (VERIFIED), Disney+ 720p or 480p (REPORTED, conflicting), no HDR, no surround anywhere. These are **known limits of the Linux targets**, not reasons to defer them; nothing in this project can raise them, and no Linux browser beats another on quality. Edge's doubt is about whether DRM plays, not about how well.

Two decisions matter more than everything else. First, **the launch mode is `--app=<url>` in a dedicated persistent `--user-data-dir`, never `--kiosk`**: Edge kiosk runs InPrivate and officially does not run extensions (VERIFIED), which silently defeats the whole overlay design that 00 proposed. Second, **how the extension gets installed**, which is now **decided (user, 2026-09-28)**: an **unlisted listing in both the Chrome Web Store and Edge Add-ons, force-installed through the registry policy** (`ExtensionInstallForcelist` under `HKLM\SOFTWARE\Policies\...`). This works on every Windows edition including Home with no user steps, because browser policy is a registry read and the AD-domain condition in the vendors' docs applies only to *off-store* sources (VERIFIED by the controller against both vendors' policy pages, 2026-09-28; it corrects R3's framing that policy itself needs a domain). `--load-extension` is gone from branded Chrome (VERIFIED) and the escape flag went in Chrome 142 (REPORTED, SYNTH), so nothing in the design leans on it. That decision covers the Chromium flavor on Windows; on Linux the same store-hosted extension would be force-installed from a JSON policy file, which is an inference for Chrome and UNKNOWN for Edge (§4.4). The Firefox flavor's route follows from the browser-target decision and is described in §4.4. The single biggest *unknown* is whether any of `--app=` (Firefox: `-kiosk`), a custom profile, a loaded extension or an attached CDP session lowers the resolution a service delivers; no source says yes and no source says no, and it has to be measured on hardware before any design work.

**Firefox is a first-class target on both OSes, beside Chrome and Edge (decision).** It adds no quality anywhere (Netflix 1080p on every OS despite its PlayReady CDM; parity with Chrome on Linux, R5), so it is the choice for users who want it, with a known 1080p SDR stereo ceiling on Netflix on Windows. It costs a second extension flavor: AMO signing, a Firefox manifest, a per-profile sideload of the signed XPI (README D10; R7), with `ExtensionSettings` force-install policy kept only as the fallback, and a second native-messaging registration (R5, R6). On Linux the snap problem is avoided by decision: StreamFlex detects a full Firefox by probing for a real application directory, and when no usable browser is installed its installer offers all three, defaulting to Firefox (README D9; R6). **Safari** is the one browser that beats Edge, and only on Netflix (2160p, HDR/DV per secondary sources) and Apple TV+ (2160p HDR, VERIFIED), at the price of a whole new platform: a macOS launcher port that upstream flex-launcher does not have, an Xcode container app, a $99/year developer account, and no silent enablement without a supervised Mac. **Backburnered by decision** (macOS out of scope until StreamFlex is popular).

## 4. Recommended architecture

### 4.1 Browser per OS

Targets are decided (README.md): **like-for-like, Edge, Chrome and Firefox on both Windows and Linux; on Linux, Firefox means the full (non-snap) build.** Users choose among the three on either OS. macOS is backburnered.

- **Windows: Edge is the recommended default; Chrome and Firefox are supported targets.** Edge is the only path to HDR/DV and 5.1/Atmos on Netflix and matches Chrome everywhere else. Chrome's known limit is SDR stereo on Netflix (4K SDR on Chrome 140+, default state UNKNOWN, §6). Firefox's known limit is Netflix 1080p SDR stereo (R5).
- **Linux: Chrome, Edge and full Firefox, at one quality level where DRM plays.** Chrome and Firefox are Widevine L3 (R1; R5 §1.4), so neither is preferred on picture. **Edge on Linux may not play DRM at all** (UNKNOWN, leaning "no" on current stable: a Microsoft-side answer says Widevine is "not available on Linux now", VERIFIED fetch; one user reports breakage in Edge 143, REPORTED; R6 "Linux Edge and Widevine"). **Decided (user): Linux Edge is a non-DRM browser** (YouTube, Jellyfin, Plex, Twitch and the like) until Phase 0 item 27 passes; if it fails, Linux Edge stays for non-DRM services only. An `--enable-features=msWidevinePlatform` switch was offered by the Microsoft-side answerer as a "possible workaround", unconfirmed by anyone (UNKNOWN). **Chrome means Google's branded `google-chrome`, not Chromium**, which has no CDM and "will not play at all" (R3, Alternative D); this matters on Raspberry Pi OS, whose archive carries Chromium and no Firefox (VERIFIED, R6 §2). Edge exists on Linux; its kiosk mode is unsupported there (R3 §6), which the plan does not use. **Detection** follows the Firefox rule: probe for the vendor's ELF, `/opt/google/chrome/chrome` and `/opt/microsoft/msedge/msedge`, never a `PATH` name, which can find wrapper scripts or Chromium (R6 §6.4; the Edge path VERIFIED from package scripts, the Chrome ELF name REPORTED). **Flatpak Chrome and Edge are excluded like the Firefox snap:** they do honor the host's policy files, but cannot reach a host native-messaging host (R6 §6.4, below in §4.4). **Architectures:** Edge for Linux is **amd64 only**; Chrome ships amd64 and arm64 (VERIFIED from both repos' package indexes, R6 §6.5). So a 64-bit Raspberry Pi can run Chrome and Firefox but not Edge, and a 32-bit ARM Pi can run neither Chrome nor Edge, leaving `firefox-esr` (R6 §2, §6.5). **Install** is simpler than Firefox's: each vendor deb configures its own apt repo on install, and Ubuntu ships neither browser, so there is no snap trap (VERIFIED from the maintainer scripts, R6 §6.5). For Firefox, the snap is excluded by decision: StreamFlex **detects** a full Firefox by probing for a real application directory (§8a.1, R6 §1) and, when no usable browser of any of the three is found, the installer **offers all three, defaulting to Firefox** (README D9; mechanism in R6 §2–3, §6.5–6.6). An unconfined Firefox reads `/etc/firefox/policies/policies.json` and `~/.mozilla/native-messaging-hosts/` directly (VERIFIED, R5 §1.2, R6 §4–5), which is what removes the snap's portal problem.
- **One extension source, two WebExtension flavors** (R5 §1.3 INFERENCE, agreed): the **Chromium MV3 build serves Chrome and Edge on Windows and Linux** (four browser installs, one package per store), and the **Firefox build serves Firefox on both OSes**. All content-script code (engine, focus ring, adapters, adapter fetch, key handling) is shared; per-flavor glue is two generated manifests (`background.service_worker` vs `background.scripts`; `browser_specific_settings.gecko.*` Firefox-only), a shadow-root API wrapper, and two native-host registrations. Details in §8a.1.
- **Do not embed** (Electron, CEF). **WebView2 is the one alternative worth a Phase 0 measurement** because it does support SL3000 (VERIFIED): if an evergreen WebView2 shell reaches 2160p on Windows 11 24H2+, it removes the whole extension-deployment problem on Windows (the shell owns the DOM via `AddScriptToExecuteOnDocumentCreated` and has trusted input via the host window). It carries the 24H2 regression risk and loses Linux, so it is a fallback, not the plan.

### 4.2 Launch mode (Chromium: not `--kiosk`; Firefox: `-kiosk`)

**Edge and Chrome (Windows and Linux):** `msedge.exe --app=<url> --start-fullscreen --user-data-dir=<per-service> --no-first-run --disable-session-crashed-bubble` (Chrome: same switches; on Linux add `--ozone-platform=wayland|x11` explicitly, as in the first draft of this synthesis). Reasons: Edge kiosk is InPrivate and runs no extensions (VERIFIED); `--app=` gives a chromeless window; fullscreen via `--start-fullscreen` or an F11 the launcher sends. Whether extensions run in `--app=` windows is R3's expectation, not verified — Phase 0 item. Autoplay: rely on the D-pad Enter being a real gesture plus accumulated Media Engagement in the persistent profile; v1 has no auto-next (README D3), so this matters only if a site's own "next episode", started by a remote press, is blocked; if so, use the `AutoplayAllowlist` policy (VERIFIED durable route) rather than `--autoplay-policy` (REPORTED as no longer honored). **Switch to Alternative B (CDP-only, no extension, `--kiosk` allowed)** only if no extension deployment route survives Phase 0 for a Chromium browser; Alternative B is Chromium-only as described (CDP), so it cannot rescue the Firefox targets.

**Firefox (Windows and Linux):** `firefox -kiosk <url> -profile <absolute per-service dir> -no-remote`, plus **`-wait-for-browser` on Windows** (VERIFIED, Mozilla wiki via R5 §1.5). `-kiosk` opens the URL fullscreen without UI (Firefox 71+, VERIFIED). **No source says extensions are disabled in Firefox `-kiosk`**, and AMO kiosk-helper extensions require it (REPORTED, positive indicator only), unlike Edge's kiosk; confirm on the real target (Phase 0 items 19, 25). On Windows `firefox.exe` is a launcher process that "always appears to exit very quickly" unless `-wait-for-browser` is passed (VERIFIED); the Job Object (§4.10) covers it either way. Linux uses the full build found by detection (§8a.1), started by absolute path, never `command -v firefox` (on Ubuntu that can be the snap stub, R6 §1). The Chromium-only pieces of this section have no researched Firefox equivalent yet: `AutoplayAllowlist`, and the `--user-agent` switch the YouTube `/tv` recipe needs (§4.9); both are open items (§9).

### 4.3 Profile

One **persistent** `--user-data-dir` (Firefox: `-profile <dir> -no-remote`) **per service**, under StreamFlex's data directory. Reasons, all from the files: it makes the spawned PID the real browser (single-instance forwarding, R4); it is required for any CDP attach (Chrome 136+, VERIFIED); it keeps logins and Media Engagement per site; it lets the YouTube profile alone carry a spoofed `--user-agent`; and it isolates a broken site's state. Cost: sign-in once per service, which is once per site anyway. Alternative: one shared profile with tabs — rejected because it breaks exit detection and the UA override. Disney+/Hulu may share one profile after the merger. Scope note: policy is per *install* or per OS user, never per profile, on every engine (VERIFIED, R7 §1), and a profile is the only scope boundary both engines have. So **the profile is also where the extension gets scoped** (README D10, §4.4): on Firefox the launcher sideloads the XPI into each per-service profile; on Chrome and Edge the policy-installed extension stays inert outside StreamFlex profiles.

### 4.4 Extension deployment — DECIDED for Chrome/Edge; Firefox route follows from the targets

**Decision (user, 2026-09-28): the Chrome/Edge extension ships as an UNLISTED listing in both the Chrome Web Store and Edge Add-ons, and is force-installed through the registry policy.** The StreamFlex installer writes `ExtensionInstallForcelist` under `HKLM\SOFTWARE\Policies\Microsoft\Edge` and `HKLM\SOFTWARE\Policies\Google\Chrome` (admin once, at install); the browser installs and updates the extension from the store with no user steps. This works on every Windows edition, Home included, because browser policy is a registry read and the vendors' AD-domain condition applies only to *off-store* sources (VERIFIED by the controller against both vendors' policy pages, 2026-09-28: Edge, "for Windows instances not joined to a Microsoft Active Directory domain, forced installation is limited to apps and extensions listed in the Microsoft Edge Add-ons website"; Chrome, off-store only on AD/Entra-joined or Chrome Enterprise Core-enrolled). **On Linux** (Chrome and Edge are targets, decision) there is no registry; policy is a plain JSON object of policy names, with no wrapper, in a directory (R6 §6.1):
- **Policy directories.** Chrome: `/etc/opt/chrome/policies/managed/` (VERIFIED, Chromium source `policy_paths.cc` and Google's Linux quick-start). Edge: `/etc/opt/edge/policies/managed/`, REPORTED by three independent third-party sources, including the Flathub Edge launcher; **Microsoft documents no Linux support**, and its `ExtensionInstallForcelist` page lists Windows, macOS, Android and iOS only (VERIFIED absence, R6 §6.1–6.2). Use one file per browser directory, e.g. `streamflex.json`.
- **Several managed files: last file wins, per policy.** Chromium reads every file in the directory, sorts the names, and gives each top-level policy the value from the lexicographically last file that sets it (VERIFIED, Chromium source `config_dir_policy_loader.cc`). A list such as `ExtensionInstallForcelist` is therefore **replaced, not merged**, across files (R6's reading of the loader), and Google's docs call a policy set in two files "undefined". StreamFlex writes its own file and, if another file already sets `ExtensionInstallForcelist` (an IT-managed box), detects the conflict and tells the user rather than shadowing or being shadowed. This is the Chromium counterpart of Firefox's first-found no-merge rule (below), and it needs different merge logic (§6).
- **Force-install.** Chrome: `ExtensionInstallForcelist` is supported on Linux, and the domain/enrollment rule is written for Windows and macOS only, so **no domain join is needed** (VERIFIED, Chromium policy definition); Linux is even the one platform where an off-store CRX is allowed (VERIFIED, Chrome for Developers). That an **unlisted** store item force-installs by ID is **inferred, not documented**: unlisted items are served to anyone with the link, and the default update URL is the store's (R6 §6.2). Edge on Linux: **undocumented**, not disproved; Edge is Chromium and reads the same layout, but it is UNKNOWN until tested (`edge://policy`), including whether an unlisted Edge Add-ons item counts as "listed in" the site (R6 §6.2). Phase 0 item 26.
- **Side effect:** any policy file makes the browser show managed status (REPORTED, R6 §6.1); expect a "managed by your organization" indicator, exact wording untested.
- **Flatpak builds** (`com.google.Chrome`, `com.microsoft.Edge` on Flathub): the launcher scripts **merge the host's policy files** into the sandbox (VERIFIED, both launcher scripts), but **native messaging cannot reach a host binary** from the sandbox, and no native-messaging portal exists (REPORTED from third-party issues; VERIFIED portal list), so treat them as unsupported, exactly like snap Firefox (R6 §6.4).

Consequences of the decision:
- **Adapters are data, not code.** Per-site selectors ship as remotely fetched JSON, which MV3 permits (only remote *code* is banned), so a selector fix needs no store review. The engine and any MAIN-world helper are code and go through review; keep them small and stable.
- **Two store accounts, two review pipelines**, each with its own cadence and policies; "unlisted" hides the listing from search but not from review. Budget for it in the maintenance loop.
- The extension ID differs per store unless the same key is uploaded to both; the policy entry names the ID plus the store update URL, so the installer writes one value per browser.
- Native Messaging is unaffected on Windows: host registration is an ordinary `HKCU` key on every edition (VERIFIED, controller). On Linux the host manifest is a file, with no policy needed: Chrome reads `/etc/opt/chrome/native-messaging-hosts/` system-wide and `~/.config/google-chrome/NativeMessagingHosts/` per user; Edge reads `/etc/opt/edge/native-messaging-hosts` and `~/.config/microsoft-edge/NativeMessagingHosts` (both VERIFIED from the vendors' docs, R6 §6.3). Edge's per-user location sits in the user data directory, so a non-default `--user-data-dir` moves it (VERIFIED), which favors the system-wide directories for per-service profiles. Edge has no documented Linux fallback to Chrome's directory, so write the manifest into both; `path` must be absolute, and `allowed_origins` lists both store IDs (R6 §6.3).
- No `--load-extension`, no debug pipe at launch, no developer-mode nag, no self-hosted CRX or update XML, no `.pem` to lose.
- **Scope (README D10):** `ExtensionInstallForcelist` is machine- or OS-user-wide, so the extension also lands in the user's everyday Chrome/Edge profile (VERIFIED, R7 §1). The decided answer is to keep the policy install but make the extension **inert outside StreamFlex profiles**, through a per-profile switch rather than a per-launch environment variable, because a URL forwarded into an already running everyday browser carries no environment (R7 §2(a)). R7's recommended shape: the launcher opens the first URL with a marker; the content script, at `document_start`, writes `storage.local.streamflexActive=true`, which is per-profile; `connectNative` stays behind that flag, so the native host is never spawned in the everyday profile. The launcher can also set the flag through the native-messaging handshake if a site strips the marker (UNKNOWN which is cleaner). What remains visible in the everyday browser is an inert, unremovable icon and a "Managed by your organization" indicator (REPORTED, R7 §2(a)). **Phase 0 also probes CDP `Extensions.loadUnpacked`** as a profile-scoped alternative with no policy at all (item 34); R7 would prefer it if branded stable still honors `--enable-unsafe-extension-debugging` (UNKNOWN, R7 §2(d)).

**Firefox flavor (Windows and Linux).** Follows from the browser-target decision; signing is decided (D11), and so is the install route (D10): **a per-profile sideload is primary, and policy force-install is the fallback.**
- **Install, primary (README D10; R7 §2(c)):** before each launch, the launcher creates the profile directory if missing, writes `user.js` with `user_pref("extensions.autoDisableScopes", 0);` (and `extensions.enabledScopes` if needed), copies the signed XPI to `<profile>/extensions/<addon-id>.xpi`, then starts `firefox -kiosk -profile <dir> -no-remote`. Basis: on release builds the profile's own `extensions/` directory is still a sideload location (`extensions.sideloadScopes` defaults to `SCOPE_PROFILE` without `MOZ_ALLOW_ADDON_SIDELOAD`; VERIFIED, Firefox source), and Mozilla's 2020 sideload shutdown left the profile scope, where add-ons "are currently installed disabled" (VERIFIED, bug 1602839), which is what the `autoDisableScopes` pref overrides (REPORTED). It writes **no policy file**, needs no admin or root, has no Windows Home question and no `/etc` merge problem, and leaves the everyday Firefox untouched. Open points, all Phase 0 items 28–33: whether plain `user.js` is honored on release 156 (one support thread says the pref cannot be set that way, about autoconfig on ESR; UNKNOWN); the file name inside `extensions/` (UNKNOWN); whether overwriting the XPI counts as an upgrade (UNKNOWN; else `update_url`); host permissions with no install prompt (UNKNOWN); and Mozilla's "initially" suggesting the profile scope could close later. Copy only before launch, to avoid corrupting `extensions.json` (R7).
- **Install, fallback (if the sideload fails Phase 0):** the Chrome/Edge approach, i.e. policy force-install (the two bullets below) plus the same per-profile inert switch (README D10; R7 §4, which ranks a launcher-owned Firefox copy last, because on Linux that copy ignores its own `distribution/policies.json` whenever `/etc/firefox/policies/policies.json` exists, VERIFIED, R6 §5, R7 §2(b)).
- **Signing:** every XPI must be AMO-signed; `browser_specific_settings.gecko.id` is mandatory. Unlisted self-distribution skips listing review but keeps automated validation, "up to 24 hours" to sign, and possible later manual review; updates come from a JSON `update_url` manifest over HTTPS, and the XPI must be served as `application/x-xpinstall` (VERIFIED, Extension Workshop, R5 §1.1). **Decided (user, README D11): unlisted on AMO**, self-distributed and signed, matching the Chrome and Edge store decision. StreamFlex therefore hosts the signed XPI and an `update_url` manifest, or ships the XPI in its package and points `install_url` at a `file:///` path, which Firefox re-installs when the file changes (VERIFIED from Mozilla's docs, untested end to end, R6 §5). An unlisted XPI with no `update_url` will not self-update from AMO (VERIFIED, R6 §5). Each engine release is one AMO signing round; adapters are remote JSON data, so they pay nothing.
- **Force-install, Windows (fallback only):** `ExtensionSettings` with `installation_mode: force_installed`, written by the installer under `HKLM\Software\Policies\Mozilla\Firefox` (REG_MULTI_SZ per Mozilla's admin reference, VERIFIED; a third-party guide says an `Extensions` subkey, REPORTED, so check on a real install). **No domain or managed-device gate is documented** (VERIFIED by absence plus vendor practice; **untested on Windows Home**). Prefer the registry to `distribution\policies.json`, which a Firefox update can delete (REPORTED). `updates_disabled: false` forces updates from Firefox 152 (VERIFIED). R5 §1.1.
- **Force-install, Linux (full Firefox; fallback only):** `/etc/firefox/policies/policies.json` for package installs, which survives Firefox upgrades; `<app dir>/distribution/policies.json` only for a tarball build that ignores `/etc` (R6 §5 recommendation). **No-merge rule:** Firefox reads `/etc/firefox/policies/policies.json` first and, if it exists, uses it *instead of* `distribution/policies.json`; it is a first-found file, not a merge (VERIFIED, Firefox source, R6 §5). So if another product already owns `/etc/firefox/policies/policies.json`, StreamFlex must **merge** its `ExtensionSettings` entry into that file, never replace it, and must not expect a `distribution` file to add to it. Mozilla's own deb (155) and tarball (156.0.1) are built with `MOZ_SYSTEM_POLICIES: true` and read `/etc/firefox/policies/policies.json`, the tarball even from `/opt` (VERIFIED, R6 §5, by inspecting `AppConstants`); Debian ESR, Arch and Fedora are REPORTED, untested. Verify at runtime with `about:policies` (REPORTED).
- **Scope trap: decided (README D10).** Policies are per Firefox *install*, not per profile (VERIFIED, R7 §1), so a policy install would land the overlay, locked, in the user's everyday Firefox. The sideload above avoids that entirely: no policy is written. Only if the sideload fails does the trap return, and then the per-profile inert switch limits it to an inert, unremovable extension in the everyday profile (R7 §4).
- **Host permissions:** from Firefox 127 users can grant or revoke host permissions ad hoc; whether a sideloaded or `force_installed` extension gets them with no install prompt is **UNKNOWN** (R5 §1.3; R7 §2(c)). The extension must check at runtime; if they are not granted, declare the streaming domains as `content_scripts.matches` and re-test (R7 §5). Phase 0 item 31 (sideload), and items 19 and 25 (fallback).
- **Native Messaging:** Windows `HKCU\SOFTWARE\Mozilla\NativeMessagingHosts\<name>` (32-bit registry view checked first since Firefox 64, VERIFIED, R5 §1.2). Linux: write the per-user `~/.mozilla/native-messaging-hosts/<name>.json` for every flavor, which every non-sandboxed build reads (VERIFIED, MDN), and also ship the system manifest from the package (`/usr/lib/mozilla/native-messaging-hosts/` in the deb, `/usr/lib64/...` in a Fedora RPM); Firefox reads exactly **one** system dir per build, chosen at compile time (VERIFIED, Firefox source, R6 §4); for Mozilla's deb and tarball it is `/usr/lib/mozilla` (VERIFIED, R6 §4, from `libxul.so`), while distro builds may use `/usr/lib64` (Fedora untested), so the per-user file is what avoids the `lib`/`lib64` question. The Firefox host manifest lists **`allowed_extensions`** (gecko IDs), not Chrome's `allowed_origins`; same host executable, second manifest.

**Linux browser detection and install (README D9; R6).** When no usable browser is installed, the installer offers all three, **defaulting to Firefox** (D9). Chrome and Edge install from the vendor `.deb`/`.rpm`, which sets up its own apt repo, with no pin and no snap trap; Edge is amd64-only, so an ARM box is offered Chrome and Firefox only (R6 §6.5). Full Firefox, the default and the harder case: Detection probes for a real application directory (an ELF `firefox` or `firefox-bin` beside `application.ini` or `omni.ja`) in known locations (`/usr/lib/firefox`, `/usr/lib64/firefox`, `/usr/lib/firefox-esr`, `/opt/firefox`, `~/.local/opt/firefox`, and the realpath of `firefox` on `PATH`); it never trusts a package name or `/usr/bin/firefox` (R6 §1). Snap-only and flatpak-only both count as "no full Firefox". The prompt lives in the **app, not the package**: a first-run and Settings check shows a dismissable fullscreen dialog only when no usable browser is found (Firefox pre-selected; R6 §3 proposed the wording "Firefox (full version) is highly recommended" for the Firefox-only version), and its button runs a `pkexec` helper that branches on `/etc/os-release` (Ubuntu: Mozilla APT repo **plus the pin**, without which the transitional `1:1snap1` package outranks Mozilla's by epoch and reinstalls the snap; Mozilla's official form is `Package: *` at priority 1000 for `packages.mozilla.org` plus, on Ubuntu, `Package: firefox` from `o=Ubuntu` at -1, written as two stanzas in one file because Mozilla's article writes both to the same filename, VERIFIED, R6 §2; Debian and Pi OS: `firefox-esr`; Fedora: `dnf`; Arch: `pacman`; otherwise Mozilla's tarball, x86_64 and aarch64 only). Packaging adds only Arch `optdepends` and Debian `Suggests: firefox-esr | firefox`; **never `Recommends: firefox`** (on Ubuntu that pulls the snap), nothing in postinst (Debian policy: maintainer scripts may have no terminal). Do not remove the snap automatically. Under D9 the prompt is suppressed whenever any usable browser is present, which covers R6's "never when the user chose a Chromium-family browser". R6 §2–3, §6.6; whether a `pkexec` polkit prompt can appear over a controller-driven fullscreen SDL UI on every session type is UNKNOWN (Phase 0 item 24).

### 4.5 Injection: MV3 content script; CDP versus Native Messaging

- **Overlay = MV3 content script, ISOLATED world**, on each service's `matches`, with `all_frames: true` and `match_origin_as_fallback: true` so blob/srcdoc player frames get it (guard double-init). Focus ring and menus live in a **Shadow-DOM host with `adoptedStyleSheets`** so page CSP cannot touch it (R3's reasoning, mine agreed, needs a check per site). A **MAIN-world helper only on Netflix**, bridged by `CustomEvent`/`postMessage`, for the internal seek API.
- **Firefox flavor differences** (R5 §1.3): MV3 is supported but the background is an **event page** (`background.scripts`), not a service worker (VERIFIED); `world: "MAIN"` is supported from Firefox 128 (VERIFIED), and it is needed there for the same Netflix helper because Firefox content scripts see the page through **Xray wrappers** (VERIFIED); closed shadow roots via `browser.dom.openOrClosedShadowRoot` or the older `element.openOrClosedShadowRoot`, both spellings appear, so feature-detect (VERIFIED); `chrome.*` and `browser.*` both exist, and Chrome ships `browser.*` from 148 (VERIFIED), so the polyfill can go if Chrome 148+ is assumed. Per-service behavior of the target sites in Firefox is **UNKNOWN** (R5), so a Firefox-specific adapter quirk is possible even though the adapter format is shared. Debian and Pi OS get `firefox-esr`, which lags the extension APIs (REPORTED, R6 §2); set the Firefox manifest's minimum version with ESR in mind.
- **Extension ↔ launcher channel = Native Messaging** (`chrome.runtime.connectNative`, length-prefixed JSON over stdio to a host the launcher registers). Reasons: standard, no automation residue, no policy needed for the host registration on any Windows edition (an ordinary `HKCU` key, VERIFIED by the controller), and it gives the extension a way to say "Home at top level", "player state", "need a trusted click here". The host manifest's `allowed_origins` must list the extension ID from each store (they differ unless the same key is used), which is the one detail to get right at install. Firefox uses a second host manifest with `allowed_extensions` (the gecko ID) and its own registration (§4.4); the API (`runtime.connectNative`) is the same (VERIFIED, R5 §1.3).
- **CDP** is reserved for one job: trusted input when SendInput/uinput cannot do it (coordinate clicks without moving the real cursor), and for the development loop (`Extensions.loadUnpacked`). It is **not** the injection path: `Page.addScriptToEvaluateOnNewDocument` lands in the MAIN world, so page CSP applies and closed shadow roots are unreachable. Alternative B (CDP-only) exists as the fallback if an installed extension itself is shown to lower DRM quality, and nothing else. Everything CDP does here is Chromium-only as researched; on Firefox the launcher-side SendInput/uinput path (§4.6) is the only trusted-input route in the files.

### 4.6 Trusted input: launcher-side SendInput/uinput versus CDP

**Primary: no injection at all for navigation.** The remote's HID keys already arrive as real, `isTrusted: true` keyboard events; the content script handles arrows/Enter/Backspace in the capture phase and moves focus itself. **Injection only for what a synthetic event cannot do**: `requestFullscreen()`, gesture-gated media start, typing into a focused field from the on-screen keyboard, and a site's documented hotkey when the site checks `isTrusted`. For those the extension asks the launcher over Native Messaging and the launcher does **`SendInput` on Windows** (works only when the browser is foreground, which it is; UIPI means same-or-higher integrity) or **`uinput` on Linux** (kernel virtual keyboard, works under Wayland where app-level injection is forbidden; needs `/dev/uinput` permission). **CDP `Input.dispatchKeyEvent`/`dispatchMouseEvent`** is the alternative when a coordinate click is needed without moving the real cursor (it requires a debug pipe or port at launch, which the decided deployment route no longer needs for anything else); it is `isTrusted: true` and grants user activation (VERIFIED); it is Chromium-only, so for Firefox (both OSes) SendInput/uinput is the whole story. Synthetic events are `isTrusted: false` in Firefox as in Chrome (R5 §1.3). Never `dispatchEvent(new KeyboardEvent)` for anything that matters.

### 4.7 Navigation engine

A **custom geometric engine with per-site adapters**, not a library. Norigin/LRUD need the app to register focusables (wrong fit); the WICG polyfill is archived; the Chromium flag is an experiment that may not exist. The engine: collect visible focusables (`a[href], button, [tabindex], [role=...]`) walking shadow roots recursively with `openOrClosedShadowRoot`; nearest-in-direction scoring per the WICG spec algorithm; `MutationObserver` for lazy rows; `scrollIntoView({block:'center'})`; a large TV-style ring. Adapters (JSON, fetched from a launcher-served or repo-hosted URL with a bundled fallback): row and tile selectors, row memory (Up/Down keeps the column), carousel paging via the site's arrow buttons, player-control selectors, explicit initial focus per route, and **per-service policy flags**: the ad-skip ban (README D2: banned per service, YouTube TV first; the adapter data carries the ban and the **engine enforces it**, so an adapter cannot map a key to an ad-skip control where the flag is set). **Cursor fallback mode** (D-pad moves a virtual pointer; synthetic `mousemove` for hover UI) is what saves the day when an adapter breaks, and the evidence (NetflixController, Kodi, Language Reactor) says adapters will break.

### 4.8 Player control

**v1 acts only on remote presses (README D3):** every action the overlay takes answers one key press; there is no auto-skip (intro, recap or ads) and no auto-next, and automatic actions are revisited per service later. A "skip intro" is a button the user presses, never a timer. Player mode switches the key map when a `<video>` is playing. Send the site's **documented** hotkeys as trusted keys: Netflix (Enter/Space, F, Esc, Left/Right 10 s, Up/Down volume, M, S skip intro — VERIFIED) and Prime (Space, F, Esc, Left/Right, M, C subtitles, A audio — VERIFIED); Disney+ and Max have no reachable official list (UNKNOWN), so click their real buttons via adapter selectors. **Never set `video.currentTime` on Netflix** (M7375, REPORTED 2026); use Left/Right or the MAIN-world `playerApp.getAPI()` seek bridge (REPORTED current, smoke-test each release). On non-Netflix sites `currentTime` is probably safe but unverified per service. Media keys (Play/Pause, Next, Prev) need no code: Chrome/Edge's global media-key hook already drives the media session. Firefox's media-key handling was not researched (§9); until measured, assume the launcher may need to translate media keys for Firefox. Set `disablePictureInPicture` on the `<video>`.

### 4.9 The YouTube `/tv` special case

**Decided (README D4): the `/tv` UA rule with a fallback to the standard site.** Primary recipe: the YouTube profile is started with `--user-agent=<PS4 Leanback / Cobalt string>` and `--app=https://www.youtube.com/tv`. Fallback: when the `/tv` UI does not load (UA rejected, or no UA override on that browser), launch the standard `youtube.com` with the normal engine and a YouTube adapter. D2's ad-skip ban applies to YouTube first. No adapter, no DRM, 4K/60 (REPORTED). Quality follows window size, so the window must be fullscreen at native resolution. Leanback already understands arrows/Enter/Backspace; the overlay should stay out of the way there (the content script can `matches` the domain only to provide Home and the cursor fallback). It is the only service where a TV UI loads; do not spend time trying TV UAs on the others (Netflix errors E109; Amazon "wouldn't help"; Peacock blocks Linux; all REPORTED). **Firefox gap:** `--user-agent` is a Chromium switch; the files have no researched per-profile UA override for Firefox, so until one is found Firefox (both OSes) takes D4's fallback to the standard site, while Chrome and Edge on both OSes get `/tv` (§9).

### 4.10 Hand-off with StreamFlex

Ship **B + D from R4**: Home **closes the browser**; the extension asks the launcher over Native Messaging (D) and the launcher's own low-level key hook / `RegisterHotKey` is the backstop that works even if the page is hung. Closing means `WM_CLOSE` to the browser's top-level windows, then a Job Object kill after a timeout. Reasons: it is the only clean design on GNOME Wayland (VERIFIED focus-stealing prevention), it sidesteps every `SetForegroundWindow` rule on Windows, and it stops playback. **Exit detection: a Job Object with a completion port** (`JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO`) around the spawned-suspended browser, plus a watch on the main PID (VERIFIED technique); on Linux, a process group and `waitpid`. Edge's `StartupBoostEnabled`/`BackgroundModeEnabled` policies must be off for the process to actually exit (REPORTED; whether a private profile is affected is UNKNOWN). Firefox on Windows: pass `-wait-for-browser`, because `firefox.exe` otherwise exits at once while the browser keeps running (VERIFIED); a 2021 bug puts the launcher process in a job when that flag is set (REPORTED), so the StreamFlex Job Object must coexist with it (R5 §1.5; SYNTH: nested jobs should allow this, check in Phase 0 item 5). On Linux the process group plus `waitpid` covers Firefox as it did Chrome. Design A (launcher stays resident and raises itself, `SDL_HINT_FORCE_RAISEWINDOW`) is a later optimization, gated on the focus prototype.

### 4.11 Normalizing remote and gamepad input

**Normalize at the edge, so the overlay sees exactly one input path: keyboard.** Remotes: program the FLIRC/CEC bridge/air-mouse to emit arrows, Enter, **Backspace for Back** (Esc accepted as alias; Chrome no longer navigates on Backspace, REPORTED), a launcher-owned key for Home, VK_APPS for the overlay menu, and media keys as-is. Long-press Back = Home, detected by `event.repeat` count. Gamepads: **the launcher (SDL) already reads them natively**; while the browser is foreground it translates buttons to the same keys via SendInput/uinput (SYNTH: SDL2 needs `SDL_HINT_JOYSTICK_ALLOW_BACKGROUND_EVENTS=1` to receive joystick events while unfocused — my knowledge, verify). In-page Gamepad API is a later nicety: it only works in the focused page, after a first button press, and never in the launcher path. CEC needs a Pulse-Eight adapter because desktop GPUs do not wire the CEC pin (REPORTED).

## 5. How it fits StreamFlex

Launcher (C99/SDL2) versus extension (JS). Config-format details are my inference; the user knows StreamFlex's config better than the files do.

**Launcher code (StreamFlex):**

1. **A `web_app` entry type / launch recipe** in the menu config: `url`, `browser` (edge|chrome|firefox on both OSes; on Linux, chrome means `google-chrome`, never Chromium, and firefox means the full build found by detection), `profile` name, optional `user_agent`, optional extra flags, `home_closes` (default true). The launcher composes the command line from these (Chromium `--app=`, Firefox `-kiosk -profile -no-remote`, §4.2) rather than the user hand-writing `Command=`.
2. **Per-service profile directory management**: `<streamflex-data>/profiles/<service>/` created on first launch, passed as `--user-data-dir` (Chromium) or `-profile` (Firefox). One directory per browser per service, since the profile formats differ (SYNTH). **For Firefox, before every launch** (README D10; R7 §2(c)): write `user.js` with `extensions.autoDisableScopes=0` and copy the signed XPI to `<profile>/extensions/<addon-id>.xpi`, only while Firefox is not running. That is the Firefox extension install; no policy is written.
3. **Process supervision**: Windows Job Object + completion port, spawn-suspended/assign/resume, wait for active-process-zero, plus main-PID watch (Firefox: also `-wait-for-browser`); Linux process group + `waitpid`. Timeout-then-kill on Home.
4. **Home key path**: Windows `WH_KEYBOARD_LL` on a dedicated thread (callback in microseconds; re-arm on a timer because Windows silently drops slow hooks, VERIFIED) or `RegisterHotKey` if the chosen key allows it; Linux: GlobalShortcuts portal where available (GNOME 48+, KDE; bound to app identity, one `BindShortcuts` per session, VERIFIED) or reading the remote's evdev device directly (SYNTH design, what CEC-to-uinput projects do).
5. **Native Messaging host**: a small stdio executable (or the launcher itself). Linux Chrome and Edge: the same manifest (`allowed_origins` with both store IDs, absolute `path`) in `/etc/opt/chrome/native-messaging-hosts/` and `/etc/opt/edge/native-messaging-hosts/` (VERIFIED, R6 §6.3). Flatpak Chrome/Edge cannot reach it and are unsupported (R6 §6.4). Speaks length-prefixed JSON; messages: `home`, `close`, `send_keys`, `click_at`, `player_state`, `adapter_version`.
6. **Trusted-input service**: `SendInput` (Windows) / `uinput` device (Linux, udev rule installed by the installer) used by both the Native Messaging host and the gamepad translator.
7. **Extension bootstrap (installer, not launcher)**: write `ExtensionInstallForcelist` for both browsers under `HKLM\SOFTWARE\Policies\...` (admin once, at install; Home has no gpedit so the installer is the only writer) with each store's extension ID and update URL. Firefox needs **no** installer step: it is sideloaded per profile (item 2; README D10). Firefox policy (`ExtensionSettings` `force_installed` under `HKLM\Software\Policies\Mozilla\Firefox`, key form to confirm, §4.4) is written **only in the fallback**, if the sideload fails Phase 0. On Linux (root once): `ExtensionInstallForcelist` into `/etc/opt/chrome/policies/managed/streamflex.json` (VERIFIED path) and `/etc/opt/edge/policies/managed/streamflex.json` (REPORTED path; Microsoft documents no Linux support), each after checking the directory for another file that sets the same policy (last file wins, lists are not merged, R6 §6.1); and, **in the Firefox fallback only**, the `ExtensionSettings` entry into `/etc/firefox/policies/policies.json`, **merging into an existing file rather than replacing it** (first-found, no-merge rule, R6 §5), or into `<app dir>/distribution/policies.json` for a tarball build that ignores `/etc`. Also write the Edge hygiene policies in item 10. Optional developer switch in the launcher: spawn with `--remote-debugging-pipe --enable-unsafe-extension-debugging` and `Extensions.loadUnpacked` a local checkout, for iterating on the extension without a store round-trip.
8. **Gamepad → key translation** while the browser is alive (SDL background joystick events → SendInput/uinput), so gamepads and remotes are indistinguishable to the overlay.
9. **Display hygiene**: `SetThreadExecutionState(ES_DISPLAY_REQUIRED)` / `SDL_DisableScreenSaver` while the browser is alive (the browser's wake lock covers playback, not browsing); park the mouse pointer in a corner at launch; optional refresh-rate switch (`ChangeDisplaySettingsEx`; v1 = manual "match 24p" toggle or a fixed 120 Hz mode, per-title later); optional HDCP/HDR readiness warning (feasibility UNKNOWN).
10. **Edge policy hygiene** for the profile: `StartupBoostEnabled=0`, `BackgroundModeEnabled=0`, `AutoplayAllowlist` for the service domains.
11. **Linux browser check (README D9; R6 §1–3, §6.4–6.6)**: run the detection probes (full Firefox; `/opt/google/chrome/chrome`; `/opt/microsoft/msedge/msedge`) at startup and when Settings opens (a few `stat()` calls, no state file); only when no usable browser is found, show the dismissable dialog offering all three, Firefox pre-selected (Edge hidden on non-amd64); its button runs a separate `pkexec` helper (e.g. `/usr/libexec/streamflex/install-browser`) that installs the vendor package for Chrome or Edge, or, for Firefox, branches on `/etc/os-release`, and falls back to showing the commands as text when `pkexec` is missing. Packaging: Arch `optdepends`, Debian `CPACK_DEBIAN_PACKAGE_SUGGESTS` `firefox-esr | firefox`, never `Recommends: firefox`, nothing in postinst (R6 §3; the CPack setting is untested). No prompt when any usable browser is present (D9).

**Extension code (new sub-project):**

- Two generated MV3 manifests from one source (Chromium: service worker; Firefox: event page plus `browser_specific_settings.gecko`), a shadow-root API wrapper, content script (ISOLATED) per service, MAIN-world Netflix helper, Shadow-DOM overlay host, geometric engine, adapter loader (remote JSON + bundled fallback), player mode, on-screen keyboard (native-setter + `InputEvent` recipe, VERIFIED for React), cursor fallback, `cursor:none` while in D-pad mode, `disablePictureInPicture`, Native Messaging client, YouTube `/tv` pass-through, Backspace/Esc handling in the capture phase at the top window and inside frames.

**What carries over from the Android TV / Fire TV lessons (ATV file), and what does not:**

- *Native engine overriding synchronous `.focus()`; `preventDefault` does not stop it* — **does not carry over** as stated. Desktop Chromium has no native spatial-navigation engine unless `--enable-spatial-navigation` is set, and the overlay's capture-phase `stopPropagation`/`preventDefault` **does** stop the site's own arrow handlers. That is one more reason not to turn the Chromium flag on beside a custom engine: with it on, the lesson applies in full and the two engines fight.
- *Defer with `setTimeout(0)`, save/restore scroll* — **carries over as a defensive pattern**, for a different opponent: site code that reacts to focus or to the same keydown by scrolling carousels or re-rendering virtualized rows (Netflix). Expect to need it in adapters, not in the core.
- *Competing handlers produce bouncing focus (`.stop` on children)* — **carries over as a design rule**: exactly one owner per key per mode (overlay or site, never both). Player mode hands Left/Right to the site; browse mode keeps them.
- *Fire OS trusted-input gate: `.focus()` does not land until a real input arrives; synthetic events don't satisfy it* — the specific `.focus()` gate **does not** exist in desktop Chromium (SYNTH inference; it is Amazon's fork), but the **same mechanism does carry over** three ways: `requestFullscreen()`, autoplay-with-sound and `getGamepads()` all need real user activation, and `isTrusted: false` events never grant it. This is the reason 4.6 says SendInput/uinput/CDP and never `dispatchEvent`.
- *Explicit initial focus on every route entry* — **carries over verbatim**. Netflix/Disney+ are SPAs; on each route change (browse → title → player → back) the adapter must set an initial focus or the first D-pad press does nothing, which on a couch reads as "broken".
- *Test the two platforms separately* — carries over as: test Edge, Chrome and Firefox separately, on Windows and on Linux separately (six combinations); a green run on one is not a proxy for another.

## 8. Prototype path

Each phase is the smallest spike that de-risks the next decision. Nothing is built until Phase 0 is measured.

**What the 2026-09-28 decisions change in the order.** Firefox moves from "build only if both stores reject the extension" to a target on both OSes, so its deployment tests join the Phase 0 minimum, and the Firefox flavor is built alongside the Chromium one from Phase 2 instead of being kept on paper. Linux stays last, and after the like-for-like decision it covers all three browsers: the Chromium build and the Firefox build are both already proven on Windows by then, so the Linux-only work is Firefox detection/install, per-browser policy and native-messaging placement (Chrome and Edge paths from R6 §6), and the process/input layer. Item 27 (does Edge on Linux play DRM at all) **is** in the Phase 0 minimum: it is cheap, and its result decides whether Linux Edge is offered DRM services at all (by decision it stays non-DRM until it passes). The Linux Chrome/Edge integration item (26) joins the minimum too, now that R6 §6 names the paths to test: whether Edge on Linux honors the policy at all decides whether Linux Edge has a zero-step install. The service order after Netflix is a `SERVICES.md` question.

**Phase 0 — Measure (no product code).** Items 1–8 of §7, plus **20 (Windows Firefox integration), 24–25 (Linux full-Firefox detection, install, messaging), 26 (Linux Chrome and Edge integration), 27 (Edge on Linux DRM) and 28–35 (the per-profile extension scope, README D10; R7 §5)**, at minimum; item 19 and the policy half of item 25 run only if the Firefox sideload (items 28–30) fails. Use stock browsers, a five-line "hello" extension in both flavors, a throwaway C spawner and a key logger page. Must prove: the quality ceiling survives the launch mode; a zero-step extension route exists on **each** target (Edge, Chrome and Firefox on Windows and on Linux); the launcher can spawn, detect exit, and get the room back on Home. If item 1 fails on every Chromium variant, the Windows quality path pivots to WebView2 (item 17) or stops. If any target fails its deployment test (2, 26 or 28, or 19/25 in the Firefox fallback), that goes back to the user as a decision, not a silent drop; a failed Firefox sideload is already decided: Firefox falls back to the Chrome/Edge approach (README D10). If Linux Edge fails item 27, the user has already decided: it stays for non-DRM services only.

**Phase 1 — Dumb launch.** StreamFlex gains the `web_app` entry, per-service profile, the Chromium `--app=` and Firefox `-kiosk` launch lines, Job Object wait (with `-wait-for-browser` for Firefox), and the low-level Home hook that closes the browser. No extension. Must prove, on Edge and on Windows Firefox: a real remote can pick a service in StreamFlex, watch a title using the site's own Tab/Enter navigation at full measured quality, and come home with one button, 20 times in a row, on the real TV.

**Re-ordered for README D7 (Jellyfin and Plex web are Tier 1).** The first prototype targets are now Jellyfin and Plex web, not Netflix. They are DRM-free, confirmed on all six browser/OS targets, including Linux Edge, which is non-DRM (`23-services-candidates.md`, `SERVICES.md`); they carry no streaming-service ToS or tamper-detection exposure; and they split the engine's job cleanly. Jellyfin's web client already has a TV layout, so the overlay only fills gaps (VERIFIED, `23-services-candidates.md`), and Plex web has no 10-foot layout, so the overlay does all the work (VERIFIED, `23-services-candidates.md`). Netflix moves to Phase 3. Phase 0 still measures Netflix, because the DRM premise has to be settled before any design either way.

**Phase 2 — Generic engine on Jellyfin and Plex web, both flavors.** The extension from one source with **two generated manifests** (Chromium MV3, Firefox), developed via the CDP `loadUnpacked` loop on Chromium (the Firefox loop is an open item, §9). At the start of the phase it is **submitted unlisted to the Chrome Web Store and Edge Add-ons, and to AMO for unlisted self-distribution signing (README D11)**, so every review cadence is known before it matters. The phase builds the geometric engine, focus ring, Backspace-as-Back, capture-phase handling, initial-focus-per-route, the shadow-root wrapper, the per-service policy flags (D2), and Native Messaging `home` (both host manifests). No adapter at first. Must prove on Edge and Windows Firefox: browse → title → play → back with the D-pad alone on a real Jellyfin server and a real Plex server; every action answers a remote press (D3); the store/policy-installed build behaves identically to the unpacked one. Chrome gets a smoke run. Which of the two is simpler to start with is a judgment call; Jellyfin's existing TV layout suggests it (SYNTH).

**Phase 3 — Netflix: engine on a DRM site, adapter and player mode.** First the generic engine on Netflix: the stats overlay still shows the Phase 0 numbers, and a one-hour soak produces no Netflix error. Then the Netflix adapter: row memory, carousel paging, player key map via launcher-sent trusted keys, a skip-intro **button on a remote press** (D3), on-screen keyboard for search, `SendInput`/`uinput` fullscreen. Must prove: a full evening's use without touching a keyboard or mouse, including one search and one sign-in.

**Phase 4 — More services and the maintenance loop.** The YouTube `/tv` recipe with its fallback to the standard site (D4; `/tv` on Chrome and Edge, the fallback on Firefox until a UA override is found, §4.9); a further service's adapter (which one: `SERVICES.md`) to validate that the adapter model generalizes, run on both flavors; adapters fetched from a remote JSON with bundled fallback; cursor fallback mode. Must prove: an adapter can be updated without shipping a launcher build, and cursor mode rescues a deliberately broken adapter.

**Phase 5 — Linux (Chrome, Edge and full Firefox).** The browser detection probes and the any-of-three install prompt (Firefox by default, D9) with its `pkexec` helper (§4.4, §5 item 11); the Firefox flavor sideloaded into each StreamFlex profile with `user.js` (README D10; `/etc/firefox/policies/policies.json`, merged and never replaced, only in the fallback); the Chromium build force-installed from `/etc/opt/chrome/policies/managed/streamflex.json` and `/etc/opt/edge/policies/managed/streamflex.json` with the multi-file conflict check (R6 §6.1; Linux Edge offers DRM services only if item 27 passed, and non-DRM services either way, by decision); native-messaging manifests for all three; refusal of Chromium and of Flatpak Chrome/Edge (R6 §6.4); `uinput` host, GNOME Wayland/KDE/X11 Home behavior, quality matrix confirmed on hardware; packaging hooks (Arch `optdepends`, Debian `Suggests`). Must prove: on a default Ubuntu (snap) box with no Chrome or Edge, the prompt appears with Firefox pre-selected and one button yields a working full Firefox (and, if chosen instead, a working Chrome or Edge); on a box that already has any usable browser, no prompt appears; the same two extension builds and adapters run unchanged; the launcher-side differences are contained in the process/input/install layer.

## 8a. Firefox and Safari

R5's own INFERENCE tag is kept where it used it. **Status after the 2026-09-28 decisions:** Firefox is a target on Windows and Linux (on Linux, the full build only), beside Chrome and Edge on both; Safari is backburnered with macOS.

### 8a.1 Firefox (target on Windows and Linux)

**Quality.** Nothing gained. Netflix lists Firefox at 1080p on Windows, macOS and Linux (VERIFIED, Netflix table) even though Firefox 132 added a PlayReady CDM "for select sites" with 4K "with key streaming partners" announced (REPORTED, gHacks 2024); no working 2160p on Firefox was found in 2026, DoveRunner documents SL3000 for Chrome only (VERIFIED absence), and no HDR/DV/5.1/Atmos source exists for any service. Hulu gives Firefox 480p (REPORTED). On Linux Firefox is the same Widevine L3 as Chrome.

**Deployment (Windows).**
- **Signing:** every XPI must be signed by AMO. Unlisted self-distribution skips listing review; automated validation, "up to 24 hours" to sign, manual review possible at any time afterwards (VERIFIED, Extension Workshop). `browser_specific_settings.gecko.id` is mandatory. Updates via a JSON `update_url` manifest over HTTPS; **each release is one AMO signing round**, but adapters are remote JSON data (decided), so only engine changes pay it.
- **Install (README D10):** primary is the per-profile sideload (§4.4; R7 §2(c)), with no policy. The policy route below is the **fallback**.
- **Force-install (fallback):** `ExtensionSettings` with `installation_mode: force_installed`; `install_url` optional for AMO-hosted extensions from Firefox 153; `updates_disabled: false` forces updates from 152 (VERIFIED, Mozilla admin docs). Written as `distribution\policies.json` beside `firefox.exe` or under `HKLM\Software\Policies\Mozilla\Firefox` (REG_MULTI_SZ; a third-party guide puts it under an `Extensions` subkey, so **the exact key form must be checked on a real install**). **No domain or managed-device gate is documented** anywhere in Mozilla's policy pages, and vendors deploy the same file on unmanaged machines (VERIFIED by absence plus practice; **UNTESTED on Windows Home**, Phase 0 item 19). Gotcha: a Firefox installer update can delete the `distribution` folder (REPORTED), so prefer the registry.
- **Scope trap (R5 INFERENCE, since VERIFIED by R7 §1; decided by README D10):** Firefox policies are per *install*, not per profile. A `force_installed` overlay lands in the user's everyday Firefox too; the D10 sideload avoids it, and R7 ranks a launcher-owned Firefox copy last. Chrome/Edge have the same property, but there the extension is scoped by `matches` to streaming domains and the user is unlikely to notice; the difference is that a Firefox user may object to a policy-locked extension they cannot remove. Whether `host_permissions` are granted automatically on a policy install is UNKNOWN (Firefox 127+ lets users revoke them ad hoc).
- **Native Messaging:** `HKCU\SOFTWARE\Mozilla\NativeMessagingHosts\<name>` (or HKLM), default value = path to a host manifest that uses **`allowed_extensions`** (gecko IDs), not Chrome's `allowed_origins`; 32-bit registry view checked first since Firefox 64 (VERIFIED, MDN). Same host executable, second manifest, second key. No policy needed.
- **Kiosk:** `-kiosk URL` since Firefox 71; `-profile <abs dir> -no-remote` for isolation (VERIFIED, Mozilla wiki). **No source says extensions are disabled in `-kiosk`**, and AMO lists kiosk-helper extensions that require being "launched with --kiosk" (REPORTED, positive indicator only). Contrast Edge, whose kiosk officially does not run extensions.
- **Exit detection trap:** `firefox.exe` on Windows is a launcher process that "always appears to exit very quickly" while the browser runs; **`-wait-for-browser`** keeps it alive until the browser exits (VERIFIED, Mozilla wiki), and a 2021 bug puts the launcher in a job when that flag is set (REPORTED). StreamFlex's Job Object supervision (§5 item 3) covers this either way; pass the flag as well.

**Deployment (Linux, full Firefox; Linux Chrome and Edge are covered in §4.4).** Unconfined Firefox (Mozilla tarball or APT) reads `/etc/firefox/policies/policies.json` and `~/.mozilla/native-messaging-hosts/` directly (VERIFIED). R6 fills in the rest, summarized in §4.4 and §5 item 11:
- **Detection** by application directory, not package or command name, because Ubuntu's `firefox` deb is a transitional snap installer (VERIFIED, R6 §1). Per-distro outcome: Ubuntu default → snap only → prompt; Ubuntu + Mozilla deb, Debian ESR, Fedora, Mint → full (Debian/Mozilla-deb paths VERIFIED, the rest REPORTED); Arch → full only if installed; Pi OS → no Firefox by default (its archive carries Chromium and no `firefox`, VERIFIED).
- **Install** per distro through a `pkexec` helper: Mozilla APT repo plus Mozilla's pins on Ubuntu (suite `mozilla`, architectures `all amd64 arm64 i386`, no `armhf`, VERIFIED; keyring, source file and pins verbatim from Mozilla's own "Install Firefox on Linux" article, VERIFIED, R6 §2; the `firefox*`/1001 form in an earlier R6 draft was a third-party variant); `firefox-esr` on Debian and Pi OS; `dnf`/`pacman` on Fedora/Arch; Mozilla's tarball elsewhere (x86_64 and aarch64 only, VERIFIED). Mozilla's deb ships no policies and no native-messaging manifests (VERIFIED), so StreamFlex writes both.
- **Prompt placement:** in the app at first run and in Settings, not in the package; Debian policy says maintainer scripts may have no terminal and must fall back to non-interactive (VERIFIED); `Recommends: firefox` would pull the snap on Ubuntu (VERIFIED basis).
- **Install:** the per-profile sideload (README D10), identical to Windows. **Policy, fallback only:** `/etc/firefox/policies/policies.json`, merged, never replaced (first-found no-merge rule, VERIFIED from Firefox source); `distribution/policies.json` only for a tarball build that ignores `/etc`.
- **Native messaging:** per-user manifest for every flavor; the system dir is one path per build (`/usr/lib/mozilla` or `/usr/lib64/mozilla`, VERIFIED from Firefox source), and `/usr/lib/mozilla` for Mozilla's deb and tarball (VERIFIED, R6 §4).

**The snap (out of scope by decision; kept for the record).** The snap reportedly reads `/etc/firefox/policies` as a fallback (REPORTED, pre-91 doc) with a 2022 counter-report and a 2025 regression where `file://` XPI installs stopped working (REPORTED); native messaging from the snap historically did not work at all, then worked through an **Ubuntu-only WebExtensions portal patch** that has never shipped upstream (VERIFIED, Firefox source docs), and the replacement **`xdg-native-messaging-proxy`** landed in Firefox 157 behind a pref (`widget.use-xdg-desktop-portal.native-messaging-proxy`, off by default) and is "available in Ubuntu 26.04+" (VERIFIED, bugzilla and Firefox docs); whether Ubuntu's current snap has flipped the pref is UNKNOWN. Flatpak Firefox: UNKNOWN. The proxy's own README calls exposing it "potentially INSECURE" because a native host is a sandbox-escape vector; keep the host manifest root-owned.

**Shared code (R5 INFERENCE, I agree).** Essentially all content-script code is shared: engine, focus ring, adapters, adapter fetch, key handling (capture-phase listeners and `isTrusted` behave the same). Per-browser glue: **two generated manifests** from one source (`background.service_worker` vs `background.scripts` event page; `browser_specific_settings.gecko.*` Firefox-only), a wrapper over `chrome.dom.openOrClosedShadowRoot` / `browser.dom.openOrClosedShadowRoot` / `element.openOrClosedShadowRoot` (both Firefox spellings appear, feature-detect), and the two native-host registrations. `world: "MAIN"` is supported in Firefox 128+ (VERIFIED). Firefox content scripts see the page through Xray wrappers, so page globals need the MAIN world there too. Chrome ships `browser.*` with promises from 148 (VERIFIED), so the polyfill is droppable if Chrome 148+ can be assumed on the HTPC.

**Verdict on Firefox — superseded by the decision.** R5 rated Windows Firefox low–medium effort with no quality gain (a fallback) and Linux Firefox medium–high (deferred), and the first draft of this synthesis agreed. The user has since made Firefox a target on both OSes (README.md), so those verdicts no longer govern. What survives as analysis: Firefox brings **no quality gain** (its Netflix cap is a known limit on Windows and costs nothing on Linux, where every browser is L3); R5's "medium–high" Linux rating was driven by the snap, which the full-Firefox decision removes, leaving roughly R5's "medium if the launcher uses a non-snap Firefox" plus R6's detection and install work; the real costs are the untested per-profile sideload (README D10; its fallback carries the per-install policy scope and the untested Windows Home force-install), the host-permission grant, the AMO signing round per engine release, and Firefox-specific site behavior that nobody has measured (§6).

### 8a.2 Safari (macOS only) — backburnered

**Out of scope (decision, 2026-09-28):** macOS is revisited only if StreamFlex gains mass popularity. The findings below are kept so that work does not have to be redone.

**Quality.** The one browser that beats Edge, on two services: **Netflix up to 2160p** (Safari 14+, macOS 11+; VERIFIED, Netflix table), with T2/Apple Silicon, a 60 Hz 4K display over HDCP 2.2 and HDR/Dolby Vision reported by secondary sources only (Netflix's table says nothing about HDR for Safari); and **Apple TV+ 2160p HDR** (VERIFIED, Apple Support; DV and Atmos only in the Apple TV app). Disney+, Prime, Max and the rest: 1080p or lower, same as Windows (VERIFIED for Disney+/Prime; UNKNOWN for Max, Hulu, Peacock, Paramount+). Netflix Atmos in Safari: UNKNOWN.

**Distribution.** `xcrun safari-web-extension-converter` wraps the WebExtension in an Xcode project with a macOS container app (REPORTED; Apple's page did not render). Apple Developer Program **US$99/year** (VERIFIED by several sources; Apple's page not fetched). **Developer ID-signed and notarized Safari Web Extensions are loadable outside the App Store from Safari 18.4** (macOS, shipped 2025-03-31; VERIFIED, Apple engineer on the developer forum); before that, only App Store extensions or the Develop-menu "Allow Unsigned Extensions" toggle, which resets per launch. **The user still enables the extension by hand** in Safari > Settings > Extensions, then grants per-site access ("Always Allow on This Website", etc.; manifest permissions do not grant page access) (REPORTED, multiple sources). **Silent enablement exists only through Declarative Device Management** (`com.apple.configuration.safari.extensions.settings`), which requires a **supervised** Mac on macOS 15+ (VERIFIED, Apple deployment guide); a home Mac is not supervised, and whether an owner can self-supervise via Apple Configurator was not researched. Unlisted App Store distribution exists but its macOS coverage was not stated on Apple's page (REPORTED elsewhere), and Mac App Store apps must be sandboxed, which complicates spawning Safari (R5 INFERENCE).

**Integration gaps.** `runtime.sendNativeMessage` works and is delivered to the extension's own Swift `SafariWebExtensionHandler`, **not an arbitrary host executable**; the app-id parameter is ignored (VERIFIED, Apple forums). `connectNative` status is conflicting/UNKNOWN; design for request/reply. The handler is sandboxed and reaches the launcher through an **App Group** (shared `UserDefaults`, a named local service) rather than XPC to the container (REPORTED). **No closed-shadow-root API** (WebKit "neutral" in the W3C CG, VERIFIED); manifest-level `content_scripts.world: "MAIN"` was not supported in the reports found (REPORTED, Safari 16.4-era). Injection timing: if the user allows the site after load, a `DOMContentLoaded`-driven script never runs (REPORTED). Safari has **no kiosk flag**; fullscreen needs AppleScript/`Ctrl+Cmd+F` with TCC Automation/Accessibility prompts (R5 INFERENCE), and the toolbar can remain visible.

**Platform cost.** **Upstream flex-launcher supports Windows and Linux only** (VERIFIED, README), so Safari means a **StreamFlex macOS port**: SDL2 is fine on macOS (VERIFIED, SDL docs; `.app` bundle, `SDL_GetBasePath()`, universal binary), but process spawning/exit detection for Safari, fullscreen control, launchd autostart, remote/CEC input, Developer ID signing with hardened runtime and notarization (REPORTED how-tos; SDL2.framework may need library-validation handling) are all new. Plus the Xcode container app, the Swift handler and the App Group bridge.

**Verdict on Safari (R5: high effort, gain on Netflix and Apple TV+ only, not now).** I agree, and would put it more firmly: the gain is **not fully verified** (Netflix HDR/DV in Safari rests on 2020-era secondary sources and Netflix's own table does not list HDR for Safari), the install can never be zero-step on a home Mac (manual enablement plus per-site allow, VERIFIED that only supervised DDM avoids it), the closed-shadow-root gap removes a tool the Chromium/Firefox build relies on, and the launcher port is a new platform for one browser. The only thing that should reopen it is a concrete Mac-HTPC user who wants Netflix or Apple TV+ 4K and accepts a one-time manual enablement. (The user's decision sets the bar higher still: mass popularity of StreamFlex.)
