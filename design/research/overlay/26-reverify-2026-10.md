## 5. Store program policies on remote configuration

**5a. Chrome Web Store (VERIFIED text).** Source: https://developer.chrome.com/docs/webstore/program-policies/policies (page footer "Last updated 2025-05-22 UTC", so unchanged since before 2026-09-28) and https://developer.chrome.com/docs/webstore/troubleshooting ("Blue Argon: Additional requirements for Manifest V3", last updated 2026-07-20 UTC). Quoted fragments:
- "the full functionality of an extension must be easily discernible from its submitted code"; "This means that the logic of how each extension operates should be self contained."
- "The extension may reference and load data and other information sources that are external to the extension" but "these external resources must not contain any logic."
- Violations: "Including a <script> tag that points to a resource that is not within the extension's package"; "Using JavaScript's eval() method or other mechanisms to execute a string fetched from a remote source"; **"Building an interpreter to run complex commands fetched from a remote source, even if those commands are fetched as data"**.
- Permitted: "Fetching a remote configuration file for A/B testing or determining enabled features" "where all logic for the functionality is contained within the extension package". Exceptions only through documented APIs (Debugger API, User Scripts API).
- Consequence: "If we are unable to determine the full functionality of your extension during the review process" Google "may reject your submission or remove it from the store."

My reading (inference, not a Google statement): selectors, URL patterns, string labels, numeric timeouts and per-service on/off flags are plainly "data". The risk is an adapter format expressive enough to be a program: conditionals, loops, "wait for X then click Y then if Z" step sequences, or expressions evaluated by a generic engine. That is the "interpreter ... even if fetched as data" wording. A design that keeps all control flow in the shipped engine and lets JSON choose only among engine-defined actions with parameters fits the "determining enabled features" example; a rule language does not obviously. The adapter schema (SERVICES.md / `20-service-schema.md`) is the place to check against this clause. The policy does not mention unlisted items.

**5b. Unlisted review (VERIFIED).** https://developer.chrome.com/docs/webstore/cws-dashboard-distribution (last updated 2020-12-07): Unlisted "does not create a listing" but anyone with the URL can install; "All visibility settings have the same policy requirements and will go through the same review process." https://developer.chrome.com/docs/webstore/review-process (last updated 2021-12-10): "All submissions go through the same review system"; "review is completed within a few days, but it can take up to a few weeks"; longer for "broad host permissions or sensitive execution permissions" (the overlay needs host permissions on the streaming sites).

**New since the research (published 2026-07-01, enforced from 2026-08-01):** https://developer.chrome.com/blog/cws-policy-updates-2026 : predictive markets prohibited; Limited Use ("Any user data collected by an extension must now be strictly necessary to the extension's disclosed single purpose"); proactive disclosure if data handling changes; new rule against extensions "designed to circumvent safety guardrails, usage restrictions, or other protective measures." The post does not mention remote code, remote configuration or modifying third-party sites. The last item is about AI guardrails; I found nothing tying it to streaming services' DRM, but a reviewer reading "usage restrictions" broadly is a theoretical reading, not something sourced.

**5c. Microsoft Edge Add-ons (VERIFIED text).** https://learn.microsoft.com/en-us/legal/microsoft-edge/extensions/developer-policies (ms.date 2026-07-24, updated_at 2026-08-13; fetched in full):
- 1.2: "Any `declarativeNetRequest` rules must be clearly declared within the extension, and should not be imported remotely unless necessary for functionality."
- 1.2.1: "your extension should not download a remote script and subsequently run that script in a manner that is not consistent with the described functionality."
- 1.1.7: "Extensions with obfuscated code aren't allowed. This includes code within your extension package, as well as any external code or resource fetched from the web."
- 1.1.1 single purpose; 1.1.2 "All functionality of an extension should be clearly disclosed to the user."
- 2.8: "Your extension must not provide unauthorized access to website content, such as by circumventing paywalls or login restrictions." and "must not provide, encourage, or enable the unauthorized access, download, or streaming of copyrighted content or media." A streaming-site remote control does neither, but this is the clause a reviewer would test a "streaming overlay" against; worded in the listing as navigation only.
- No clause about remote configuration or interpreters. Edge has no equivalent of Chrome's "interpreter" sentence. UNKNOWN how Edge reviewers treat remote JSON that is data only.
- https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension (ms.date 2026-05-05): Partner Center asks "Are you using remote code?"; "Remote code is only supported for Manifest V2, not Manifest V3. In Manifest V3, loading and executing remotely hosted code is not permitted." Visibility: Public, or `Hidden` ("Removes an extension from search results or browsing"; share the listing URL). Certification "can take up to seven business days". The page does not say Hidden items get a different review; every submission goes through the same Steps 1 to 8, so same review is the reasonable reading, but there is no sentence stating it. Answering the remote-code question "No" for adapter JSON is consistent with the policy text only if the JSON holds no logic.

**6c. Profile sideload scope (VERIFIED source; new UNKNOWN lead).**
- `toolkit/mozapps/extensions/internal/AddonSettings.sys.mjs` on Firefox main (https://raw.githubusercontent.com/mozilla-firefox/firefox/main/...): `SCOPES_SIDELOAD` is `AddonManager.SCOPE_PROFILE` unless the build sets `MOZ_ALLOW_ADDON_SIDELOAD` (or automation), where `extensions.sideloadScopes` is honored with default `SCOPE_ALL`. So on Mozilla's release builds the profile scope is still the one sideload location.
- `browser/app/profile/firefox.js` on main: `pref("extensions.autoDisableScopes", 15);` with comment "Disable add-ons that are not installed by the user in all scopes by default." Scope 15 includes profile (1), so a sideloaded XPI in the profile is disabled unless `autoDisableScopes` is lowered; this is consistent with D10's `user.js` pref.
- Bug 1602839 (https://bugzilla.mozilla.org/show_bug.cgi?id=1602839): still NEW, last change "4 years ago"; description still says profile-scope sideloading "will eventually change as well", no timeline. No new comments.
- Firefox 157 (2026-09-29) and 158 (2026-10-13) developer release notes (MDN) list no sideload, signing or policy change. Firefox 158 is the current release; I did not fetch the user-facing release notes (redirect).
- **New lead (UNKNOWN, needs a Phase 0 test):** in `XPIProvider.sys.mjs` the startup call is `XPIStates.scanForChanges(aAppChanged === false)`, and `scanForChanges` skips a location when `ignoreSideloads && !(loc.scope & startupScanScopes)`, with `startupScanScopes` read from `extensions.startupScanScopes` (default 0 in `firefox.js`) unless the app build ID changed, in which case it is `SCOPE_ALL`. Read literally: for an existing profile last used by the same Firefox build, a changed or newly copied XPI in the profile `extensions/` folder might not be re-scanned at startup; a brand-new profile or a build change would scan. I could not read `scanForChanges` as one function (the fetch tool would not reproduce it) and found no special case for the profile scope; the profile location is also where normal installs live, so the real behavior may differ. This bears on D10's open points "does overwriting the XPI count as an upgrade" and "the file name inside `extensions/`": an update-by-overwrite may only take effect after a Firefox build change unless `extensions.startupScanScopes` includes the profile scope (value 1). Test: install, then replace the XPI with a higher version, restart with the same build, check `about:addons`.

## Changes worth acting on

1. **Chrome 4K**: Chrome 143+ has hardware-secure decryption on by default in source; Chrome 140 to 142 needed the flag. Phase 0 item 1 can now state a version floor (143) and drop the flag instruction for current stable, while still measuring on a clean profile and an HDCP 2.2 chain.
2. **CWS "interpreter" clause** constrains the adapter JSON format (see 5a). Decide the adapter schema with this clause in hand; consider stating "data only, no control flow" in the schema doc and the store listing's remote-code answer.
3. **Edge Add-ons** has no remote-configuration clause, but clause 2.8 (streaming/copyrighted content) is the one to word the listing against.
4. **Mozilla policies change 2026-12-01** (enterprise add-ons, re-agreement); read the previews fully before the AMO submission.
5. **Firefox profile sideload**: add a restart-after-overwrite test to Phase 0 items 28 to 30 (see 6c); possible dependence on `extensions.startupScanScopes`.
6. **Two-week browser cadence** for Chrome, Edge and Firefox shortens the window to retest the smoke matrix.
7. New reference engines: SofaNav (generic engine), HomeTheater (adapter-per-service, WebView2).
