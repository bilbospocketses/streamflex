# 25. D10: the extension-scope trap (Firefox policy, and whether Chrome/Edge share it)

Date: 2026-09-28. Scope: Windows and Linux only. Tags: VERIFIED (read from a primary source or source code this pass), REPORTED (secondary source, forum, issue tracker), UNKNOWN (needs the Phase 0 test). Web searches used: 16 of 20.

## 0. Framing fact that changes the question

SYNTHESIS §4.3 already decides on **one persistent dedicated profile per service** (`-profile <dir> -no-remote` on Firefox, `--user-data-dir` on Chromium). So the real question is not "dedicated profile or not". It is **how the extension gets into those StreamFlex profiles without a mechanism that reaches the user's everyday browser.** A profile is the only scope boundary that exists on both engines; policy has no profile scope.

Consequence for option (a): if the everyday browser is already running, launching into it would forward the URL to the running instance (single-instance forwarding) and skip StreamFlex's kiosk/env marker. That is already why §4.3 uses a dedicated profile, so the "activate via launch marker" idea in (a) must be profile-scoped state, not an env var (see (a) below).

## 1. Does the trap exist on Chrome and Edge? Yes, same shape, one extra Windows wrinkle

- Firefox policy: per installation, all profiles. VERIFIED (Mozilla: "Policy is intended to work per machine or per operating system user, not individual profiles"; files live in the install's `distribution/`, or `/etc/firefox/policies`). https://firefox-admin-docs.mozilla.org/guides/policies-configuration/ , https://support.mozilla.org/en-US/kb/customizing-firefox-using-policiesjson
- Chrome/Edge `ExtensionInstallForcelist`: machine-wide (HKLM) or OS-user-wide (HKCU), or `/etc/opt/chrome/policies/managed/` on Linux. No per-`--user-data-dir` scope. VERIFIED for the paths (file 24 §6, Chromium policy docs). https://chromium.googlesource.com/chromium/src/+/HEAD/docs/enterprise/policies.md
- **Windows-only wrinkle, applies before scope even matters:** on Windows not joined to AD/Azure AD/Chrome Enterprise Core, Chrome force-installs only Chrome Web Store items, and Edge only Edge Add-ons items. VERIFIED (Google Help policy text, quoted via search) https://support.google.com/chrome/a/answer/7532015 ; REPORTED for Edge (one Microsoft Q&A thread, which also claims Windows 11 is exempt; a single user report, treat as UNKNOWN) https://learn.microsoft.com/en-us/answers/questions/2379289/why-is-edge-extension-force-install-policy-restric . So on an HTPC that is a Windows Home box, Chrome/Edge policy install needs a store-listed (unlisted OK) extension; a self-hosted CRX will not force-install.
- Firefox has **no** such Windows-Home gate (policy is file/registry only). README's Windows Home note stands.

So the trap is uniform in shape, but the escape hatches are not uniform, which is the real finding (see the table in section 4).

## 2. Options

### (a) Accept it: install by policy, make the extension inert outside StreamFlex

- Works? Firefox Windows/Linux: yes (`ExtensionSettings` `force_installed`, VERIFIED shape, file 24 §5). Chrome/Edge Linux: policy paths VERIFIED, Edge-on-Linux force-install UNKNOWN (file 24). Chrome/Edge Windows: yes for store-listed extension, subject to the non-domain gate above.
- User-visible effects (everyday browser): extension listed and unremovable in `about:addons`/`chrome://extensions`; Firefox shows the "managed by your organization" state (REPORTED, not tested), Chrome/Edge show "Managed by your organization" on the menu and `chrome://policy` (REPORTED). A toolbar icon unless `default_area`/`toolbar_pin` hides it (Firefox `default_area` VERIFIED in file 24; Chrome `toolbar_pin` in `ExtensionSettings`, not re-read).
- Cost: the extension's content script matches only the streaming domains, and wakes in an everyday tab on Netflix (the extension code executes there, and needs host permissions granted, UNKNOWN for policy installs on Firefox, file 15).
- Design for inertness, if chosen: the switch must be **per-profile storage, not per-launch env**. Env var inherited by the native host does not exist when a URL is forwarded into an already running everyday browser. Recommended shape: the launcher opens the first URL with a marker (query or fragment); the content script, running at `document_start`, sees the marker and writes `storage.local.streamflexActive=true`; from then on that profile is active. `storage.local` is per-profile, so the everyday profile never gets the flag. Keep `connectNative` behind that flag so the native host is never spawned in the everyday profile. Failure mode: a site that redirects and strips the marker before the content script runs on first launch (mitigate: the launcher can also write the flag via the native-messaging handshake from the StreamFlex side, since the host only runs when the flag or handshake exists; UNKNOWN which is cleaner).
- Maintenance: lowest. Root/admin write for the policy at install (Linux: `/etc/...` needs root; Windows: HKLM or `distribution\policies.json` needs admin). Windows Firefox installer updates can delete `distribution\` (REPORTED, https://support.mozilla.org/en-US/questions/1237979); use registry or re-write at launch (file 15).
- Failure modes: first-found policy file on Linux (if the user already owns `/etc/firefox/policies/policies.json`, StreamFlex must merge, VERIFIED file 24); the user cannot remove it, and cannot even opt out of the popup icon on Chrome/Edge without another policy; uninstalling StreamFlex must remove the policy or the force-install stays as an orphan (whether Firefox uninstalls the add-on when the entry is removed is UNKNOWN, file 24).

### (b) Dedicated Firefox copy for StreamFlex

- Works? Windows: an extracted Firefox in StreamFlex's directory with its own `distribution\policies.json` next to `firefox.exe` (VERIFIED location, file 15). Linux: tarball in StreamFlex's directory with `<dir>/distribution/policies.json`. **VERIFIED trap on Linux:** the tarball also has `MOZ_SYSTEM_POLICIES: true` and Firefox reads `/etc/firefox/policies/policies.json` FIRST, and only falls back to `<appdir>/distribution/policies.json` if the /etc file does not exist (file 24 §5, from `EnterprisePoliciesParent.sys.mjs`). So on a Linux box where the user (or the distro's Firefox package) has an /etc policy file, the dedicated tarball **ignores its own policy and inherits the user's**. Isolation fails exactly where the user has customized Firefox. Windows registry policies (HKLM/HKCU `Software\Policies\Mozilla\Firefox`) likewise apply to every install (REPORTED, inferred from docs), so use the file route only.
- User-visible effects: none on the everyday Firefox. A second Firefox in the app-menu only if StreamFlex registers it.
- Cost: highest. StreamFlex must download, verify and update a whole browser (~70 MB Windows zip class, ~80 MB Linux tarball class; sizes not measured). Self-update for an extracted Windows Firefox and for the Linux tarball is UNKNOWN as to what works unprivileged. Widevine is downloaded **per profile** into `gmp-widevinecdm` on first use (REPORTED), which the per-service profile decision already incurs, so a second Firefox adds no extra Widevine download beyond the per-profile one; it also needs the first-run download online and `media.eme.enabled` (file 15 covers EME). https://support.mozilla.org/en-US/questions/1166450
- Distro packages of D9 ("offer any of three browsers") would be replaced by a StreamFlex-owned tarball for Firefox only, which contradicts the goal of using the user's installed browser (D9 offers to install one; a tarball path is a different product decision).
- Verdict: works, but the cost is out of proportion when (c) scopes the same thing at no browser-management cost.

### (c) Normal (non-policy) install into the dedicated profile

Can a signed unlisted XPI be preinstalled into a profile without policy on release Firefox? **Yes by the source, with one required pref; needs a hands-on confirm.**

- VERIFIED (Firefox source, `AddonSettings.sys.mjs`): `SCOPES_SIDELOAD` "is a bitflag for what scopes we will load new extensions from when we scan the directories"; pref `extensions.sideloadScopes` defaults to `SCOPE_ALL` only when the build defines `MOZ_ALLOW_ADDON_SIDELOAD`, **otherwise `SCOPE_PROFILE`**. So on release builds the profile's own `extensions/` directory is still a sideload location. https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/mozapps/extensions/internal/AddonSettings.sys.mjs
- VERIFIED (Mozilla, bug 1602839 text): sideloading closed for everything "other than the profile"; "extensions sideloaded through the profile will not change behavior initially (they are currently installed disabled, and are removable)". https://bugzilla.mozilla.org/show_bug.cgi?id=1602839 . The 2020 announcement is about installers dropping add-ons into app-wide locations, not the profile folder; manual XPI install is stated to remain. https://blog.mozilla.org/addons/2020/03/10/support-for-extension-sideloading-has-ended/
- "Installed disabled" is the `extensions.autoDisableScopes` default (REPORTED: default 15 covers profile scope), so the launcher also writes `user.js` with `extensions.autoDisableScopes` = 0 (and `extensions.enabledScopes` = 15 if needed). Usage of these two prefs to enable profile-installed add-ons is REPORTED in Mozilla support threads; geckodriver documents that user.js prefs override its recommended ones (VERIFIED for the mechanism: https://firefox-source-docs.mozilla.org/testing/geckodriver/Profiles.html). One support thread claims `autoDisableScopes` "cannot be changed by customized configuration file" (that thread is about autoconfig on ESR, REPORTED, https://support.mozilla.org/en-US/questions/1175052): confirm that plain `user.js` is honored on release 156. UNKNOWN until tested.
- Recipe: launcher creates the profile dir if missing, writes `user.js`, copies the signed XPI to `<profile>/extensions/<addon-id>.xpi` (file named exactly the add-on ID, REPORTED https://support.mozilla.org/en-US/kb/deploying-firefox-with-extensions for the `distribution/extensions` variant; profile variant same naming, UNKNOWN), then starts `firefox -kiosk -profile <dir> -no-remote`.
- Signing: the unlisted-channel signed XPI installs permanently on release (VERIFIED, file 15; https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/). Unsigned needs Nightly/Developer/unbranded builds, so signing is mandatory (D11 already decides unlisted-on-AMO).
- User-visible effects: none outside StreamFlex profiles. The extension is removable inside the StreamFlex profile (fine; the launcher re-copies it on the next launch).
- Maintenance: low. Updates: overwrite the XPI when StreamFlex updates and rely on Firefox re-scanning the profile location at start-up (mtime/size check; UNKNOWN whether it treats a replaced file as an upgrade). Alternative that is known-good: have a bundled `update_url` in the manifest (file 15, VERIFIED for the mechanism; UNKNOWN for a sideloaded profile install). No admin/root needed, no policy file, no Windows Home gate, no `/etc` merge problem. It also removes the VERIFIED Linux first-found-policy hazard.
- Failure modes: (1) `autoDisableScopes` is ignored in `user.js` (then install stays disabled and the Phase 0 test fails loudly); (2) Mozilla closes the profile scope later (bug text says "initially"; watch `extensions.sideloadScopes` in release notes); (3) host permissions for an MV3 content script not granted when there is no install prompt (UNKNOWN; same as file 15's policy note); (4) first run needs the Widevine download per profile, and a bare profile has no logins (already accepted, §4.3); (5) a corrupt `extensions.json` from copying while Firefox runs (mitigate: copy only before launch).
- Other profile-scoped route noted, rejected: launching with Marionette (`--marionette`) and `Addon:Install` permanent install. It works on release Firefox in principle (REPORTED) but sets automation flags that streaming sites may detect. Not recommended.

### (d) Chrome and Edge equivalents of (c)

- `--user-data-dir` + `--load-extension`: **dead on branded Chrome.** VERIFIED that Chrome 137 removed it from branded builds behind the `DisableLoadExtensionCommandLineSwitch` feature (Chromium PSA, https://groups.google.com/a/chromium.org/g/chromium-extensions/c/1-g8EFx2BBY/m/S0ET5wPjCAAJ). REPORTED that the `--disable-features=DisableLoadExtensionCommandLineSwitch` workaround worked on 137 to 141 and **stopped working in Chrome 142**; Chrome for Testing, unbranded Chromium and other Chromium browsers (Brave) still accept the flag. https://github.com/seleniumbase/SeleniumBase/issues/4053 , https://github.com/SeleniumHQ/selenium/issues/16540 . One search snippet contained developer-mode boilerplate that tripped the prompt-injection scanner; the content was ordinary issue text and nothing in it asked for anything.
- **Edge:** no Microsoft source found saying `--load-extension` is removed or kept on stable Edge; Microsoft's own doc only describes the Load unpacked UI (https://learn.microsoft.com/en-us/microsoft-edge/extensions/getting-started/extension-sideloading). A Playwright issue reports the flag not loading on Edge (REPORTED, https://github.com/microsoft/playwright/issues/24063, undated relevance). Treat as **UNKNOWN**; test on the pinned Edge in Phase 0.
- **Chrome for Testing / Chromium as a dedicated browser** (the (b) analog): keeps `--load-extension`, but stock Chromium ships **without Widevine** (license), so it cannot play Netflix/Disney+/Prime DRM (REPORTED, https://groups.google.com/a/chromium.org/g/chromium-discuss/c/zuamXTE5G40 and Chromium build docs). For a streaming launcher that is disqualifying. Not viable.
- **CDP `Extensions.loadUnpacked`:** the supported successor of the flag. Requires `--remote-debugging-pipe` (not the port) plus `--enable-unsafe-extension-debugging`; installs per browser session, so the launcher calls it every launch (REPORTED: Puppeteer `installExtension`, web-ext issue #3388; https://github.com/mozilla/web-ext/issues/3388 , https://github.com/puppeteer/puppeteer/issues/14536). UNKNOWN whether branded stable Chrome 142+ and Edge still honor `--enable-unsafe-extension-debugging` in 2026. It is profile-scoped, needs no policy, and works on unlisted/unpacked builds. SYNTHESIS already flags CDP-pipe as the Alternative B plumbing and item 1(d) measures that the pipe does not degrade quality. Risk: an attached debugger can fingerprint as automation (UNKNOWN), and the unpacked extension may show a developer-mode warning bar (UNKNOWN).
- **One-time store install per profile** (open the store page in the StreamFlex profile, user clicks Add): works on branded Chrome and Edge with no policy and no flags, persists, auto-updates from the store. Cost: one couch-remote click **per service profile** (SYNTHESIS uses one profile per service), so N clicks, and a page that may not be D-pad friendly. Store presence is already required by the store decision.
- **Chrome/Edge external-extension JSON/registry** (`HKLM\Software\Google\Chrome\Extensions\<id>`, `/opt/google/chrome/extensions/<id>.json`): is machine-wide too, so it has the same scope problem as policy. Not researched further.

## 4. Recommendation

**Answer is not uniform, but the principle is: scope the extension by profile, never by installation.**

1. **Firefox: option (c).** Sideload the signed unlisted XPI into each StreamFlex profile's `extensions/` folder and set `extensions.autoDisableScopes=0` in that profile's `user.js`. No policy file is written at all, so the trap disappears and StreamFlex needs no root/admin, no Windows Home workaround and no `/etc/firefox/policies` merge. It also removes the VERIFIED first-found-file hazard that would defeat option (b) on Linux.
2. **Chrome and Edge: keep policy (a) as the baseline only where it is legal, and prefer CDP `Extensions.loadUnpacked` if Phase 0 shows branded stable still honors it.** Failing that, accept (a) with the profile-scoped inert switch described above. Do not use `--load-extension` (dead on branded Chrome 142+) or Chrome for Testing (no Widevine).
3. **Always ship the profile-scoped inert switch** (storage flag written on first StreamFlex-launched navigation, native host spawned only when the flag exists) so that if (c) or the CDP route fails and StreamFlex falls back to policy, the everyday-browser cost is an inert icon rather than a running extension.
4. Reject (b) unless (c) fails Phase 0. Fallback ladder for Firefox: (c), then (a), and only then (b).

## 5. Phase 0 hands-on test that confirms this

Same Windows box and one Linux box (Mozilla tarball, `/opt/firefox`), release Firefox 156.x, everyday Firefox installed and running with its own profile.

1. Sign a trivial content-script extension (unlisted, `web-ext sign`) that on `https://example.com` sets `document.title`.
2. Fresh profile dir. Copy the XPI to `<profile>/extensions/<id>.xpi`, write `user.js` `user_pref("extensions.autoDisableScopes", 0);`. Run `firefox -profile <dir> -no-remote about:addons`. **Pass:** extension shows enabled with no prompt, content script runs, it survives a second launch. Repeat WITHOUT `user.js` to confirm the "installed disabled" default (UNKNOWN, confirms the pref matters) and once with `-kiosk` to confirm the extension runs in kiosk.
3. Replace the XPI with a version 2 file and relaunch. **Pass:** about:addons shows v2 (confirms overwrite-to-update; if not, test `update_url`).
4. In the everyday Firefox: **Pass:** the extension is absent from `about:addons`, `about:policies` shows nothing StreamFlex-related, no "managed" indicator.
5. MV3 host permissions: with the extension declaring `host_permissions` for `https://*.netflix.com/*`, confirm the content script actually injects with no install prompt (file 15's UNKNOWN). If not granted, add the streaming domains as `content_scripts.matches` and test again.
6. Widevine: in the fresh profile load a Netflix page and confirm `gmp-widevinecdm` is downloaded on first run; note the delay (file 24/15 assume it).
7. Negative test for the trap: write a policy `force_installed` entry and confirm it appears in the everyday Firefox (VERIFIED by docs, one-minute confirm), so the rejection of (a) for Firefox is measured rather than inferred.
8. Chrome/Edge (branded stable, pinned): launch with `--user-data-dir=<dir> --remote-debugging-pipe --enable-unsafe-extension-debugging`, send `Extensions.loadUnpacked`; record pass/fail, any developer-mode banner, and whether `navigator.webdriver` stays false. Also try `--load-extension` on Edge stable to close the Edge UNKNOWN.
9. Linux policy first-found check for (b)/(a): with an existing `/etc/firefox/policies/policies.json` present, confirm the tarball ignores `<appdir>/distribution/policies.json` in `about:policies`.
